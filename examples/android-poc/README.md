# Android on-device POC

Proves `datum-connect-daemon` (this repo) and `datumctl` can run **on an Android phone itself**,
not just be consumed by an app. Full loop:

phone camera photo → tiny on-device HTTP server (NanoHTTPD) → on-device `datum-connect-daemon`
tunnels it to a public `*.datumproxy.net` hostname → viewed back on the same phone via WebView,
round-tripping through the real Datum Cloud proxy.

Verified end-to-end, including with the phone on cellular data only (Wi-Fi off), so the round
trip is not a local-network shortcut.

## What's not in this directory

Three things are required to build/run this but are intentionally not committed:

1. **`app/src/main/jniLibs/arm64-v8a/libdatumdaemon.so`** and **`libdatumctl.so`** — the daemon
   (this repo) and `datumctl` cross-compiled for `aarch64-linux-android` / `android arm64` and
   renamed with a `lib*.so` extension (the standard trick to get exec permission past Android's
   W^X restriction, same pattern VPN/tunnel apps use):
   ```
   # daemon, from connect/connect-lib in this repo
   rustup target add aarch64-linux-android
   cargo install cargo-ndk
   cargo ndk -t arm64-v8a build --release -p daemon

   # datumctl
   GOOS=android GOARCH=arm64 CGO_ENABLED=0 go install go.datum.net/datumctl@latest
   ```
   Copy both into `app/src/main/jniLibs/arm64-v8a/` as `libdatumdaemon.so` / `libdatumctl.so`.

2. **`app/src/main/assets/sa-creds.json`** — a Datum service-account credentials file
   (`datumctl login --credentials sa-creds.json --hostname auth.datum.net`), used for headless,
   non-interactive auth on-device (no browser/keyring available). Mint one for your own project
   and drop it here.

3. **`local.properties`** — standard Android SDK path, generated by Android Studio on first open.

## Key runtime requirements (wired into `TunnelService.kt`)

- `HOME` must point at a writable directory (Android's default `HOME=/` is read-only) —
  otherwise `datumctl` fails with `mkdir /.config: read-only file system`.
- `SSL_CERT_DIR=/system/etc/security/cacerts` — Android has no `/etc/ssl/certs`; this points
  rustls at Android's real system CA store instead.
- The daemon's `endpoint` field (from `GET /v1/tunnels`) is always an ephemeral local inspector
  port, not the real target — the app persists its own tunnel ID (`filesDir/tunnel_id.txt`) the
  first time it creates a tunnel and reuses it on every subsequent run, to avoid orphaning cloud
  tunnel resources every launch.

## Viewing tunnel content from a desktop browser

`*.datumproxy.net` responses come back with `Content-Type` (and, for compressible types like
`text/html`, `Content-Encoding`) stripped, which breaks a real browser hitting the tunnel
directly. `pc_relay.py <tunnel-hostname> [port]` works around this: it fetches the tunnel over
HTTP/1.1 with `Accept-Encoding: identity` and re-serves with the correct `Content-Type` at
`http://127.0.0.1:8123/`.
